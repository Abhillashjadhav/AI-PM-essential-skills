# Technical decisions

These are reversible engineering choices made while building V1. The product decisions are the owner's and are listed in the [PRD](../../prds/2026-09-25-model-router.md). None of the choices below reopens them.

| # | Decision | Why | Reversibility |
|---|---|---|---|
| D1 | Python 3.11 standard library only; SQLite (WAL) for state | The spec requires it; it adds no production dependencies | High |
| D2 | The coordinator runs **inside** the terminal process. Cross-process safety comes from SQLite: a dispatch lease, compare-and-swap job transitions, and unique constraints. There's no Unix-socket daemon yet | The spec allows a socket; tests show the unique constraints and lease prevent duplicate handoffs and dispatches across two clients (S06). A daemon can be added later without changing the core | High |
| D3 | JSON Lines JSON-RPC to `codex app-server` (stdio). Messages don't include a `jsonrpc` field | Matches the upstream schema (`JSONRPCRequest` has `id`, `method`, `params`, `trace`) and the upstream test client, which writes JSON plus `\n` | High |
| D4 | The executable model ID is Codex `Model.model` (the slug). `Model.id` is kept as `raw_ref` | `thread/start` and `turn/start` take a model slug. Marked INFERRED until checked on the pinned install | High |
| D5 | Model changes on an override use `turn/start.model`/`effort`; after a restart, the pinned model is passed on `thread/resume` and checked against the response | These are documented `TurnStartParams` and `ThreadResumeParams` fields. A mismatch holds the thread (S05) | High |
| D6 | `clientUserMessageId` = the local dispatch ID, used **only** to reconcile after a crash, never as an idempotency key | The field is in the schema, but whether the provider deduplicates on it is unverified. Not finding it doesn't prove nothing ran | High |
| D7 | Mark a dispatch SENT **before** writing `turn/start` | A crash between the write and the save then counts as uncertain, not as "never sent", which is the conservative direction | Medium |
| D8 | Spend decision = UNKNOWN unless a *live*, pin-bound, account-bound, unexpired enforcement record with documentation exists **and** its conditions are true at the moment of dispatch | The spec forbids treating low usage, subscription auth, credit fields or attestations as enforcement | High (only more evidence is added) |
| D9 | Missing role binding → route **up** to the next approved role; never down. If nothing is approved at or above the role, the job goes to AWAITING_MANUAL_MODEL | Consistent with "higher suitable role" and "never invent a replacement" | High |
| D10 | Required tools that no approved binding is cleared for → keep the role's binding, then block with a visible BLOCKED_CAPABILITY | Makes capability failures visible rather than silently switching model | High |
| D11 | Capacity method `capacity-range.1`: min/max of clean, comparable before/after deltas, widened by one rounding step; at least 5 observations; validation needs an owner approval. **Ships UNKNOWN.** | An engineering hypothesis, not an approved accuracy claim. The thresholds are not tuned to make the demo work | High |
| D12 | CLEAR_AND_SIMPLE evidence thresholds: at most 8 steps, at most 12 files, every step described, every interface named with a contract, concrete tests, no blocking questions or open decisions | These are hypotheses for "bounded". A model's own "this is easy" is recorded but ignored | High |
| D13 | Default handoff context budget is 400,000 characters (configurable). Above it: BLOCKED_CONTEXT, with the full package saved | The provider doesn't report a context window through `model/list`. No silent truncation | High |
| D14 | Routing timeout is 4 s, measured from submission and including attachment prep, adapter startup and discovery in the same process | Required by the spec. Eligibility waits are measured and reported separately | Owner-set |
| D15 | The weekly guardrail keeps the owner's definition. The "excluding different-task-only" variant is shown as PROPOSED. A Wilson 95% interval is used; below 20 eligible threads the report doesn't judge the 5% target | Stops the metric being quietly redefined, and stops claims on tiny samples | High |
| D16 | Approval rules for tool requests: destructive commands, credential access, external uploads and paths outside the write scope are declined automatically; everything else asks you in the terminal; never `acceptForSession`; sandbox is `read-only` for writing and `workspace-write` for coding; never `danger-full-access` | Required by the spec | High |
| D17 | A dedicated `CODEX_HOME` profile with `forced_login_method = "chatgpt"`, validated through `config/read`. The subprocess gets a minimal environment, and API-key variables are dropped | Keeps your global Codex settings untouched. The spec requires ChatGPT sign-in only | High |
| D18 | `--simulate` data lives under `<data-dir>/simulator/`, and simulator threads are marked synthetic | Synthetic threads never mix with real metrics | High |
| D19 | The live comparison runner exists but needs an authorised finite plan (at most 50 turns) and the normal gates. It gives way to waiting user jobs | The spec calls for finite, cancellable plans that give way to foreground work | High |
| D20 | The marketplace, existing skills and ContextPort are untouched. The router lives in `model-router/` | Repository rules | — |
