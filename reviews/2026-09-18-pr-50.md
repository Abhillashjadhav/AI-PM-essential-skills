# Review of PR #50: Add model-grader plugin

**Date:** 2026-09-18
**Final state:** REQUEST CHANGES — draft, not merged. Eleven defects repaired; the skill fails its own exit condition.

## Round 1 findings (reviewer role)

### Major — the skill had collapsed a gate in its own files

Hard rule 8 forbids reporting a rule complete on three of four gates. `process-discipline.md` defined four. But `status-model.md` was titled "Three statuses, never collapsed" and defined three, and hard rule 3 routed the reader **to that file** for the model. `SKILL.md`'s emit step and `CONTRACT.md`'s prose also said three, while `CONTRACT.md`'s own table already carried four columns. An agent obeying rule 8 was sent to the one reference missing the gate rule 8 names.

### Major — three decisions pre-filled in the emitted contract

`CONTRACT.md` shipped with B6's two envelope rules and C6's ranking rule written out in the interviewer's words, and an A8 placeholder reading `<answer — usually no>` with the steer inside the blank. None carried a `PROPOSED` tag, so all three would have passed freeze condition 3 while being exactly what hard rule 1 calls a guessed answer that looks decided and nobody revisits. The contract is the artifact the owner signs.

### Major — the ledger could not record a trail signal freeze requires

`process-discipline.md` names five trail signals. The second, "Decisions recorded — the owner's answer in their own words", had no section in `PROCESS_LEDGER.md`, the document that exists to hold the trail. Both prose summaries had dropped the same signal.

### Major — the contract's exit bar contradicted freeze condition 4

The approval checkbox required "Build dry-run raised zero questions" to leave DRAFT; freeze condition 4 requires only that the count be recorded and the questions logged as gaps. Under the strict reading, a dry-run that raises questions yields a permanently DRAFT contract, because the one party forbidden from answering those questions is the one holding the document — so it rewarded not running the test.

### Minor — `SKILL.md` misdescribed the bank it navigates

Part A was labelled A1–A8 but listed seven items, omitting A1 and renaming A2 to "output schema". C8 was labelled "outcome targets", which is A1's subject — so Part A was duplicated into Part C and C8 was never asked. Part B claimed all eight questions carry an observed exploit; B8's own entry says the opposite.

### Minor — headline metrics with no reachable provenance

`README.md` opened with bold "12 of 12" and "8 of 8" stated as fact. `VERIFICATION.md` is careful about exactly those figures — author-run, single domain — but none of it reached the page most readers stop at, and the grader they come from is not shipped. Under "we do not ship skills that produce unverifiable output", the README did not clear the bar.

### Minor — a project number outside the labelled example

`question-bank.md` A1's rationale used "a 0.5% wrong-rejection ceiling", four lines above "Never supply these numbers." `VERIFICATION.md` claimed those figures appeared only in `examples/catalog.md`; that claim was false.

### Minor — rendering and stale counts

README boundary table missing its `|---|---|` separator; `CONTRACT.md` A7 table with an unnamed third column; `BAR.md` saying "22 questions" against a shipped bank of 24.

## Round 1 actions (writer role)

Eleven atomic commits, one concern each:

- Stripped the three pre-filled decisions out of `CONTRACT.md`; the guidance stays in the bank, where hard rule 1 permits a recommendation to live.
- Added a `Decisions recorded` section to `PROCESS_LEDGER.md` and corrected both summaries to the authoritative five signals.
- Aligned the contract's approval checkbox with freeze condition 4.
- Corrected `SKILL.md`'s Part A list, A2 and A5 names, C8 label, and the Part B exploit claim.

## Round 2 — the exit condition, measured

The skill's own exit test had never been run. It was run here: a reviewer given `templates/CONTRACT.md` and `references/question-bank.md` only, no other file and no indication it was a test, asked what it would need before writing a grader's first check.

**Result: 18 questions. The exit condition is zero.**

Three clusters, all Part A shape questions by the skill's own classification: the contract never states what the grader is *called with*; never states what it *returns* or over what unit; and leaves reference-based versus rule-based grading undetermined. Recorded unanswered in `model-grader/OPEN_DECISIONS.md` and as Check 5 in `VERIFICATION.md`, per hard rule 1.

`VERIFICATION.md` had anticipated a second domain adding "one or two" questions. That estimate was wrong by an order of magnitude, and the file now says so.

## Gate 3 status

Every reviewer in this round was spawned by the session that made the changes, from the same context, on instructions written by the same party. That is a second sample, not a second party. Logged as `EXECUTED`, not `INDEPENDENTLY REVIEWED`. Claiming otherwise would be the precise collapse gate 3 exists to prevent, and this skill does not get an exemption from its own discipline for its own release.

## Verdict

**REQUEST CHANGES.** The eleven defects are repaired and the plugin now clears the repository's mechanical bar: valid frontmatter, nine hard rules, test input and expected output, explicit guardrails, registered in the marketplace, valid JSON.

It does not clear its own. Whether to close the 18 gaps by extending the bank, changing the contract template, or scoping them out is a product decision for the repository owner. Remains draft.
